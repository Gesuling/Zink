# ZINK project guide

This guide records the implementation visible in the current source tree for future contributors and coding agents. Source code is authoritative if this document gets stale. Keep this file updated when architecture, behavior, assets, permissions, or build setup changes. Distinguish shipped behavior from incomplete behavior and proposals.

## Product and module

ZINK is an Android icon pack and customization companion. It provides a catalog of custom app icons, launcher compatibility/apply guidance, bundled wallpapers, an icon request composer, and appearance settings. The Gradle project has one Android application module, :app, with package/namespace com.gesuling.zink.

## Architecture and technologies

- Kotlin with Jetpack Compose and Material 3, hosted by one ComponentActivity in MainActivity.kt.
- Top-level destinations are composed in MainActivity.kt; tab transitions use Compose AnimatedContent. Settings is opened as a full-screen branch from Home rather than a bottom tab.
- Feature UI and much of its static data/state are colocated by feature. There is no formal ViewModel/repository/DI/database/navigation-library layer in the current implementation.
- Shared palette/theme code is in ui/theme. ZinkPreferences persists Pure AMOLED Black and the selected Home Header Artwork through SharedPreferences. Wallpaper download quality and favourite wallpaper IDs also use SharedPreferences. Other screen selections and form state still use ordinary remember state.
- Interaction modifiers and natural-order sorting are in ui/anim/AnimationUtils.kt.
- Dependencies and Android build versions are managed by Gradle Kotlin DSL and gradle/libs.versions.toml. Current values: AGP 9.5.1, Kotlin 2.2.10, Compose BOM 2026.02.01. app/build.gradle.kts declares minSdk 26, compileSdk 37, targetSdk 37, Java compatibility 11.
- The project follows Kotlin official style. Keep feature code in the existing feature packages unless a change has a clear architectural reason.

### Navigation and main shell

Bottom destinations, in order: Home, Icons, Wallpapers, Apply, Requests. Home has summary cards and Explore rows leading to Icons, Wallpapers, Apply, and Settings. Settings is not in the bottom bar; its header gear and Explore row both open it. Selecting another tab replaces the current screen content with an animated transition. Per-screen state is generally not saveable and should be assumed to reset when the screen leaves composition or the Activity is recreated, except for explicitly persisted AMOLED preference and process-global objects such as wallpaper favorites/cache.

MainActivity enables edge-to-edge, makes the navigation bar transparent, and uses a rounded glass-like bottom navigation. Insets/padding are handled locally by the screens. Settings keeps its title/subtitle fixed above its vertically scrolling sections; the glass bottom navigation remains visible while Settings is open, and selecting a tab closes Settings. Apply keeps its title/subtitle and Current Default Launcher card fixed while search, filters, results heading/count, and launcher cards scroll in a separate viewport. Both scroll viewports reserve space above the bottom navigation.

## Visual style

The current visual direction is dark and iGlassOS-inspired: graphite/black surfaces, optional pure-black background, silver/white primary type, muted gray labels, thin translucent borders, rounded surfaces, compact letter-spaced headings, subtle scale feedback and restrained motion. The palette is available through LocalZinkColors, although screens also define their own constants. The UI is currently phone-oriented and relies on fixed dp grids/spacings; there is no adaptive multi-pane behavior.

Preserve readable contrast, the dark glass/metal hierarchy, modest motion, and edge-to-edge handling when changing UI. Existing feedback helpers are in ui/anim/AnimationUtils.kt.

## Implemented functionality

### Home and Settings

Home displays ZINK branding, header art, icon/wallpaper/favorite counts, and navigation rows. Header art options are Frieren (first-time default), Obsidian, and Nocturne. ZinkPreferences stores the selected stable artwork ID in SharedPreferences; unknown or removed IDs safely resolve to Frieren. Settings updates this shared Home state immediately, and the selection is restored when the app starts.

Pure AMOLED Black changes the background palette and is persisted with SharedPreferences through ZinkPreferences. Wallpaper Download Quality is also stored in SharedPreferences; the default is 4K Original (the bundled source dimensions). FHD 1080p limits downloaded images to a 1920×1080 landscape or 1080×1920 portrait box without upscaling smaller assets. Settings also presents Icon Masking, Apply to Launcher, Clear Icon Cache, App Version, and Developer Info. “Created by Gesuling” is an underlined link that opens https://github.com/Gesuling/Zink with an Android ACTION_VIEW intent. Several other settings rows are decorative or local-only; see known bugs below.

### Icons and launcher pack

IconsScreen has 84 static AppIconItem records, searchable by app name, package, and category, with category chips, a 3-column grid and a detail dialog that copies the package name. Catalog data is in IconsScreen.kt.

The launcher pack uses resource-nodpi PNGs and XML metadata. The appfilter mapping uses explicit ComponentInfo package/activity names and custom drawable names. Both appfilter.xml copies contain a static `<scale factor="0.74" />` fallback rule; they do not define iconmask, iconback, or iconupon artwork. This scale can affect generated fallback icons only in launchers that implement those rules; it does not apply a dark monochrome frame to ZINK's custom icons. Settings presents this fixed value as information, not as a toggle. drawable.xml enumerates icon drawables. Matching definitions are duplicated under assets and res/xml; preserve parity when editing.

The manifest registers ADW, Nova/Tesla, and Apex metadata resources and theme/icon picker intent filters. Filters include Nova/Tesla, ADW, Apex, Go, Lawnchair, and custom icon picker actions. These declarations are compatibility hooks; their presence does not establish tested behavior on every launcher/version. The manifest uses @drawable/ic_launcher_mark for both android:icon and android:roundIcon: a transparent vector canvas with the silver Z mark and no tile/background. Older adaptive and density-specific mipmap launcher assets remain in the resource tree but are no longer referenced by the manifest. The Android 12+ system splash uses dedicated light/dark Z-mark vectors via android:windowSplashScreenAnimatedIcon in values/themes.xml and values-night/themes.xml; resource night mode follows the device UI mode and is independent of ZinkPreferences.

When adding an icon, coordinate the PNG/resource name, IconsScreen catalog record, appfilter mapping, drawable catalog, and both assets/res XML copies. Verify exact package/activity identifiers. A UI catalog entry alone does not ensure launcher application.

Fallback scaling is launcher-controlled: Kvaesitso's official icon-pack documentation describes generated fallback icon support including scale and mask elements. Lawnchair's current icon-pack documentation says generated fallback icons are not implemented. Smart Launcher masking and Niagara's icon-shape behavior are launcher-owned controls; neither is connected to ZINK Settings. Treat Nova/ADW/Apex support for this fallback scale as version-dependent unless verified against the particular launcher version. References: [Kvaesitso icon-pack docs](https://github.com/MM2-0/Kvaesitso/blob/main/docs/docs/developer-guide/integrations/icon-packs.md), [Lawnchair icon-pack docs](https://github.com/LawnchairLauncher/docs/blob/main/developers/concepts/icon-packs.md), [Niagara icon-shape help](https://help.niagaralauncher.app/article/153-new-icon-shape-picker).

### Wallpapers

The static catalog in WallpapersScreen.kt contains 43 WallpaperItem records with ID, title, category, full-size resource ID, and thumbnail resource ID. Image resources are under app/src/main/res/drawable-nodpi/; names include wp_* and thumb_* with JPG, PNG, or WebP assets. Header art is also there. The app/src/main/assets/wallpapers directory exists, but current catalog references R.drawable resources; do not assume that directory is used.

Implemented interactions include a 2-column catalog with an All Wallpapers/Favourites filter, full-screen preview, pan/zoom, Fit/Original/Fill fit choices, reset, favorite toggles, download into Pictures/Zink using MediaStore with a file fallback, and applying to Home, Lock, or both with WallpaperManager. The Favourites filter reads FavouritesManager's persisted snapshot state and immediately reflects toggles; its empty state explains how to save a wallpaper. Home's favorite count observes the same state. Download quality is read when the user downloads: 4K Original decodes the full bundled resource, while FHD 1080p bounds decoding and scales the JPEG output to fit within 1920×1080 landscape or 1080×1920 portrait dimensions, preserving aspect ratio and never upscaling. Thumbnail bitmaps use an LRU cache. There is no remote wallpaper feed.

Favorites live in a process-global Compose mutableStateSetOf for immediate UI synchronization, and their stable wallpaper IDs are persisted in SharedPreferences. MainActivity restores the IDs against the current wallpaper catalog before composing Home, so counts, favorite icons, and the Wallpapers list begin in sync after restart. Unknown or malformed saved IDs are hidden from the current catalog but preserved when another favorite is toggled, allowing saved IDs to become visible again if the catalog entry returns. The bitmap cache remains in-memory.

### Apply and launcher registry

ApplyScreen queries ACTION_MAIN/CATEGORY_HOME activities dynamically through PackageManager, resolves the current default component separately, and accepts it only when it matches a concrete HOME candidate. Android setup fallback/resolver activities are excluded, and overlay/resource packages are not treated as launchers because they do not resolve HOME. It reads each app label and package from PackageManager, matches known launcher records, and adds otherwise unregistered HOME apps as installed but explicitly unsupported/unverified alternatives. The screen refreshes its launcher snapshot when Apply enters composition and when the Activity resumes; its runtime list distinguishes installed HOME apps from the selected default, and each record's DIRECT, MANUAL, or ALTERNATIVE integration method. It provides search and filters (All, Direct Apply, Manual Setup, Installed, System & Others), and opens detailed setup sheets. The fixed header includes the current-default launcher card; the searchable/filterable launcher list scrolls below it. The detail sheet's Actions section is derived from LauncherRuntimeState.actionPresentation: installed launchers get a launcher-specific OPEN action and a source link when available; uninstalled launchers get INSTALL FROM GOOGLE PLAY or DOWNLOAD FROM GITHUB; device-restricted entries show a warning; entries with no source show an availability notice. Installed direct-apply launchers also retain their 1-Tap Apply button. Play actions use package-specific market://details intents with HTTPS fallback; GitHub URLs open through ACTION_VIEW. These are outbound listing links only, and ZINK does not install apps. The 11 Play links cover Action, ADW, Apex, Lawnchair, Microsoft, Niagara, Nothing, Nova, Samsung One UI Home, Smart Launcher, and Hyperion. Kvaesitso links to its official GitHub Releases page. Pixel Launcher intentionally has no standalone installation URL and shows its preinstalled/device-restriction explanation. Google Play may still apply its own region/device compatibility restrictions. The section header presents the filtered total alongside granular confidence breakdown badges (Official, Community, Unverified), and each directory card displays its specific confidence label alongside its availability status.

LauncherRegistry currently has 15 curated entries: Nova, Niagara, Smart Launcher, Action, ADW, Original Apex Launcher (`com.anddoes.launcher`), AirBorne ApexLauncher (`com.home.launcher.apexlauncher`), Nothing, Lawnchair, Hyperion, Microsoft, Kvaesitso, Samsung One UI, Google Pixel, and Xiaomi HyperOS System Launcher (package com.miui.home; alternative-only, with no claimed standard icon-pack integration). Runtime HOME apps outside these records are added as unverified alternatives; the list is not limited to the curated package names. The Xiaomi launcher package is distinct from android.miui.home.launcher.res, a resource overlay. This mapping is sourced from community HyperOS launcher documentation and still needs confirmation on a physical Xiaomi device. Lawnchair's official Play build package is app.lawnchair.play; the prior registry omitted that current package while its listing URL already used it. The registry now recognizes Play, GitHub, nightly and legacy package variants. Official [Lawnchair build configuration](https://github.com/LawnchairLauncher/lawnchair/blob/16-dev/build.gradle) uses app.lawnchair.play for the Play flavor, and its [launcher manifest](https://github.com/LawnchairLauncher/lawnchair/blob/16-dev/lawnchair/AndroidManifest.xml) declares a MAIN/HOME activity. ApplyMethod distinguishes DIRECT, MANUAL, ALTERNATIVE. Nova is MANUAL: ZINK previously invoked the internal APPLY_ICON_THEME confirmation action, but Nova's official theme developer example documents theme discovery and Settings-based selection, not a supported external apply API. ZINK cannot observe whether the confirmation completed, so its guide now requires Open Nova Settings → Look & Feel → Icon Style → Icon Theme → ZINK. The installed-state detail offers OPEN NOVA LAUNCHER when the package exposes a normal launch intent or a package-owned HOME activity. Action remains DIRECT (the user's Xiaomi test confirms its 1-tap path works); Lawnchair and Nothing are MANUAL; Xiaomi System Launcher is ALTERNATIVE. On Xiaomi model 23129RAA4G, PackageManager resolves the old Nova action to `com.teslacoilsw.launcher/.IconThemePrompt` and its ordinary launch intent to `.NovaShortcutHandler`; this confirms the action only opens Nova's confirmation activity, not that ZINK was applied. Each LauncherSpec includes package variants, steps/settings path, requirements, limitations/troubleshooting, optional Google Play or GitHub Releases source, optional device restriction/unavailability messages, and a VerificationSource (URL, sourceType, checked date, evidence, confidence). LauncherRuntimeState.actionPresentation centralizes installed/uninstalled action labels and the fallback availability message so every registry entry has a visible Actions outcome. Launcher card, detail, and default-launcher surfaces show each installed launcher's PackageManager application icon when available; otherwise they decode that launcher's bundled fallback image from app/src/main/assets/launcher_icon_<id>.png.b64. Source provenance and licensing notes are in app/src/main/assets/launcher_icon_sources.md. The Pixel fallback is from an archived package listing; ADW fallback derives from MaterialOS artwork; Original Apex uses its authentic app icon from `apexlauncher.com`; AirBorne ApexLauncher uses its Google Play Store listing asset. Keep the per-ID asset names aligned with LauncherRegistry IDs.

If the current default launcher is not in the catalog, ApplyScreen creates an unverified alternative-only guide at runtime for that package; it does not claim standard appfilter support or offer direct apply. Settings > Apply to Launcher displays the currently resolved HOME label/package and opens the Apply tab. The default identity is refreshed when Settings or Apply resumes. If registry entries are changed, update package visibility declarations as needed.

Launcher Open actions first verify installation and resolve the requested package's own MAIN/LAUNCHER activity. If that is absent, they query ACTION_MAIN/CATEGORY_HOME with that package pinned and may open only an activity owned by that package. This supports HOME-only system launchers such as Xiaomi's com.miui.home without accidentally launching whichever launcher is currently default. If neither entry point resolves, or Android throws ActivityNotFoundException/SecurityException, the detail sheet explains that direct opening failed and offers Android's public default-app settings screen; it also explains the manual Settings path if that screen is unavailable. Package visibility includes MAIN/LAUNCHER and MAIN/HOME intent queries, plus explicit known launcher packages. A successful startActivity call means Android accepted the launch request, not that the UI was visually confirmed; test on device before claiming runtime behavior.

Direct apply creates an Intent using the registry action, constrains it to a package, adds configured extras, and calls Context.startActivity. Its Boolean result means Android accepted/launched the intent, not that the launcher confirmed icon-pack application. The Toast says an apply request was sent and asks users to confirm in the launcher if prompted; it does not report application success. On ActivityNotFoundException ZINK tries to open the launcher app and asks the user to finish selection manually. Other exceptions return false. These actions must be tested against the actual launcher/version before making stronger claims.

Registry source URLs, evidence descriptions, confidence, dateChecked, and optional installation source URLs are static records in code, not fetched or live-validated. The ADW Play page is currently available at its exact package listing; Lawnchair's current Play package is app.lawnchair.play; Kvaesitso publishes its APK releases at the official GitHub Releases URL. Verify listing package and developer before changing these records. Revisit first-party documentation/source code before publishing or upgrading compatibility confidence. Avoid asserting broad compatibility based solely on intent filters or a configured URL.

### Requests

RequestsScreen has three modes: installed unthemed apps, already-themed catalog entries, and manual entry. It scans launchable activities and excludes packages present in the icon catalog; if the result is sparse, it attempts a broader installed-package scan, then uses bundled fallback entries if no results. Unthemed apps start unselected and users explicitly select each app to include. It supports search and selection, and builds an email addressed to gesuling@gmail.com for batch/manual submissions.

Catalog request modes include a selected-count submit action. Generated emails include selected app names and package names for both unthemed and themed catalog requests; manual entry includes its name, package/link, and optional note. If email launch fails, the request text is copied to the clipboard when available, with a separate error message if copying also fails. There is no server-side submission or request history.

### Manifest/package visibility

Manifest declares SET_WALLPAPER and QUERY_ALL_PACKAGES (suppressed in lint tooling), plus MAIN/LAUNCHER and MAIN/HOME intent queries. The HOME intent query supports discovery across package IDs; explicit queries include Lawnchair's current app.lawnchair.play package and known channel/legacy variants, alongside curated launchers. Requests app discovery depends on package visibility. Reassess the declared visibility and distribution requirements if changing discovery behavior or target SDK; this guide makes no policy determination.

## Incomplete controls and known bugs

- There is no dynamic icon-masking preference. Settings shows the static 0.74 fallback scale as informational text; the app cannot toggle how another launcher consumes its packaged appfilter metadata.
- Settings > App Version is derived from package info (`v0.1.2`, API 37) and opens an interactive release changelog bottom sheet detailing v0.1.2 (22 November 2026 planned release) improvements and v0.1.1 (21 November 2026 published) release history, utilizing structured metadata (`LATEST_PUBLISHED_VERSION`) to automatically distinguish published vs planned releases.
- Transient screen selections and inputs are persisted across tab navigation and process death via SharedPreferences-backed state managers: Requests tab mode, search query, selected unthemed package checkboxes, selected themed icon IDs, and manual request form inputs (`RequestsSelectionManager`); Apply tab search query and category filter (`ApplyStateManager`); Icons tab search query and category filter (`IconsStateManager`); and Wallpapers tab favourites-only toggle (`WallpapersStateManager`). Pure AMOLED, wallpaper download quality, wallpaper favorite IDs, and Home Header Artwork selection are also persisted. Temporary modal sheets and detail dialogs (e.g., selected launcher detail sheet, selected icon dialog, selected wallpaper preview) are not persisted.

- Launcher registry records and guides are curated static data. Some source/claim details can become outdated. Granular confidence breakdown badges (Official, Community, Unverified) and card-level labels reflect registry confidence.
- Automated coverage remains limited: wallpaper output dimensions, saved wallpaper quality, bitmap decoding, favorite ID persistence/restoration and stale-ID handling, header artwork default/restoration/fallback, packaged Lawnchair/Kvaesitso launcher icon decoding, Xiaomi alternative-only metadata, HOME-candidate/default matching, and launcher Open route selection have targeted tests. The route tests verify package-scoped LAUNCHER/HOME choice and unavailable cases, but do not exercise Android PackageManager or prove a launcher visibly opened. PackageManager integration passed instrumentation on A069P (Nothing, Android 17); that device has no Lawnchair package installed, so it did not verify Lawnchair discovery or Xiaomi HyperOS behavior. The generated arithmetic and application-ID smoke tests remain.
- The XML pack declarations have copies in both assets and res/xml; drift can cause inconsistent discovery/application.

No explicit roadmap is recorded. Do not describe proposed fixes or features as planned unless a product owner confirms them in project artifacts. Useful next work is prioritized in PROJECT_STATUS.md.
